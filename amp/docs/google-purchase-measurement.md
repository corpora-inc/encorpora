# Google purchase measurement transport

`src/advertising/google-data-manager.ts` implements the Data Manager API transport for a single consented adult purchase. It is a server library, not an HTTP upload endpoint, scheduled worker or live integration. Importing it sends nothing. The application does not call it. Parent permission controls are described below. Verified-payment selection, durable delivery and refund handling must be connected before enabling live exports.

Google directs new offline-conversion integrations to Data Manager rather than the older `UploadClickConversions` endpoint. An advertiser needs Data Manager API enabled in its Cloud project, an authorized token with the `https://www.googleapis.com/auth/datamanager` scope, and access to the conversion account. The destination action must be `UPLOAD_CLICKS`; verify the action, customer-data terms and enhanced-conversion settings in the actual account. The transport does not accept terms, enable conversion settings or activate ads. See [Google's access restriction](https://developers.google.com/google-ads/api/docs/conversions/upload-offline) and [offline conversion setup](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events).

## Purchase boundary

The caller must select a server-verified, positive USD settlement and the confirmed adult purchaser's separate, current advertising permission. Child-learning consent is not advertising permission. Check withdrawal and GPC/DNT before each attempt. Do not backfill purchases that occurred before permission. Approval, invoice preparation, parent-reported submission, license activation and assessment completion are not settlement evidence.

The internal `GooglePurchase` contract contains an opaque transaction ID, the payment evidence timestamp, integer USD cents, a normalized adult email hash and permission timestamps. The type and assertions cannot prove where these values came from; only the trusted payment/permission repository can establish that. Never expose this contract as a browser-supplied upload API or populate it from arbitrary files. No learner, account, invoice or provider identifier is an acceptable transaction ID, even when hashed. Allocate a stable random export ID per destination/payment, or derive one with a dedicated keyed HMAC. Keep it unchanged across retries.

The serialized event contains only that opaque ID, timestamp, value/currency, adult email hash and consent settings. It has no learner identity, age, grade, assessment results, lesson, progress, device, IP address, browsing URL or click identifier. Inputs with extra fields are rejected. Ad personalization is explicitly denied. Hashes remain personal data and must not appear in logs or public artifacts. `googleAdultEmailHash` follows Google's [normalization rules](https://developers.google.com/data-manager/api/devguides/concepts/formatting), including Gmail dots and plus suffixes; call it only for the confirmed adult's address after permission.

`googlePurchaseRequest` defaults to validation mode and performs no network request. Its output contains personal data: inspect only through approved private tooling. `GoogleDataManager.purchase` also defaults to validation mode, but validation sends the event to Google. It therefore requires the same privacy checks as ingestion. Call with `"ingest"` only through the authorized dispatcher. The local 90-day delivery ceiling is not a guarantee that Google accepts or attributes an event; action windows and provider rules can be stricter. The library supports USD only.

## Delivery and diagnostics

The transport sends one event to one configured conversion action over a fixed HTTPS endpoint. It disables redirects, bounds the response size, limits HTTP requests to ten seconds and never retries automatically. The access-token provider must enforce its own retrieval timeout. Errors expose only fixed codes, HTTP status and whether the outcome is `not_sent`, `rejected` or `unknown`; provider bodies, credentials and payloads are not included. A timeout, network failure, server error or malformed success response may follow an accepted write. Preserve that uncertainty and reconcile before retrying.

An ingestion response produces an `accepted` receipt, not an attributed conversion. Persist the receipt and an immutable association with the dispatched payment before further work. Google processes requests asynchronously. Use `status(receipt)` after the provider's suggested initial delay; it checks the configured destination and expected record count and retains safe warning/error codes. `SUCCESS` describes processing, not proof of an ad match, paid campaign causality or additional sales. Warnings require inspection even when processing succeeds. See [Google diagnostics](https://developers.google.com/data-manager/api/devguides/diagnostics).

Before live use, the durable dispatcher must prevent concurrent delivery of one payment, preserve uncertain attempts across crashes, recheck permission, schedule diagnostics with bounded backoff, retain only necessary identifiers, and support withdrawal/export/deletion. It must reconcile platform amounts against the financial ledger. Meta delivery is a separate adapter. None of these responsibilities is performed by this transport library.

Refund delivery is not implemented here. Data Manager restates values by reusing a transaction ID; a mismatched or unknown ID can create a new conversion. Restatement also retains the conversion count. Do not send negative purchases, turn a refund into a new Purchase event, or call a zero-value restatement a retraction. Implement and verify correction handling against retained delivery receipts before optimizing bids from exported value. See [conversion adjustments](https://developers.google.com/data-manager/api/devguides/events/google-ads/conversion-adjustments).

Tests use synthetic identifiers and mocked transport responses. They cover published email formatting, strict payload exclusion, permission/time bounds, validation defaults, ambiguous writes, response limits and destination/count checks. They do not establish live account access, policy approval, API acceptance or event attribution.


## Adult permission controls

Family → Privacy → Purchase measurement records a separate, optional Google permission. It defaults off, requires an explicit adult/own-email attestation and a confirmed AMP account email, and expires after 365 days. External OIDC identities and missing account records cannot authorize sharing. The preference is part of the canonical `/me` family snapshot; an expected revision prevents stale forms from restoring a withdrawn or changed preference. An email change or notice-version change requires another explicit grant. A retry of an active grant does not extend its expiry.

The shared authenticator persists withdrawal when it receives GPC or DNT. Their absence never restores permission. Learning-consent withdrawal and learning-data deletion also withdraw it under the same exclusive account privacy lock. Preference records appear in family exports; the internal email binding digest is omitted. The privacy worker removes preferences 90 days after withdrawal or expiry. A withdrawal removes that digest immediately. A signal received before any grant creates a withdrawal revision, so an older untouched form cannot override it.

This permission is for adult purchase information; it neither authorizes sharing child information nor changes learning-consent methods. It does not activate the transport. A future dispatcher must hold the corresponding account lock through its bounded send, verify the current revision and confirmed email again, and record an immutable permission snapshot alongside each delivery receipt. Preference changes alone are not a durable historical delivery record. Do not export earlier payments after a new grant or reuse a queued payment after its permission revision changed.
