# Parent account security

With `AMP_AUTH_MODE=accounts`, **Family → Security** manages a parent's sign-in methods. These controls do not change learner access or billing.

## Passkey sign-up

A new parent can create the account with a passkey alone: email, then **Create account with a passkey**. A password stays available behind **Use a password instead** (`/sign-up?method=password`); provider buttons are unchanged. Passkey sign-up is offered where confirmation email can be delivered (the same condition as passwords) and only in a browser with WebAuthn on a domain origin. It is never offered in the native app.

- `POST /api/auth/passkey-signup/options` refuses an email that already has an account (`409 ACCOUNT_EXISTS`); the screen routes to sign-in with the email kept in memory. Otherwise it binds a WebAuthn challenge and the normalized email to a single-use server record (five minutes), referenced by a signed HttpOnly cookie. Credentials are discoverable (`residentKey: required`) so later sign-in needs no email.
- `POST /api/auth/passkey-signup/verify` consumes that record, verifies the attestation against AMP's origin and relying-party ID, then creates the parent, the passkey and the session in one transaction. The session insert rechecks that passkey under the parent lock (migration `0019`). An abandoned, cancelled, replayed, cross-site or unverifiable ceremony writes nothing. An email taken while the ceremony was open, by any method, is refused, and the unique email index settles concurrent sign-ups: no existing account ever gains a passkey this way.
- Each attempt reveals whether an email has an account, as provider sign-in already does; both endpoints are limited to ten requests per client per five minutes.
- Better Auth 1.7.10's own pre-session registration (`registration.requireSession: false` with `resolveUser`/`afterVerification`) is not used: AMP keeps `/passkey/*` registration behind a fresh, serialized session for Security.

The account starts with an **unconfirmed email**. The confirmation link is sent immediately and the parent continues into the free trial. Consent and purchase wait for confirmation; see [parent consent](parent-consent.md#confirmed-parent-email).

**Recovering an unconfirmed address.** Anyone could start an account under someone else's address. A password reset or setup link proves the address, so completing one on an unconfirmed account confirms it and removes every passkey, linked provider login and session created before. The owner keeps the account; whoever created it loses access. A parent who sets a password before confirming must add their passkey again.

- **Passkeys:** register a device or security key, give it a name, rename or remove it, and use it on the sign-in screen. WebAuthn requires HTTPS, or `localhost` for local development; a loopback IP address is not a valid relying-party domain.
- **Password:** change the password and revoke other sessions. A parent without a password can request an emailed, single-use setup link. Password sign-in and setup appear only when this deployment enables passwords.
- **Authenticator:** enter the password, scan the QR code and verify a six-digit code before activation. Save the displayed backup codes privately. Each code works once; replacing the codes invalidates the previous set. Codes are not included in ordinary settings responses or retained in browser storage.
- **Linked logins:** link or unlink configured Google, Apple, Microsoft or GitHub identities. An unavailable provider is labeled and does not count as a fallback sign-in method. Removing a method signs out other sessions. A provider sign-in with a provider-verified email links to the parent with that confirmed email, except an identity the parent removed or a parent with an authenticator; those link only from Security, which also accepts a different email.

The authenticator challenge protects **password sign-in**. Passkeys and external providers use their own authentication checks; AMP does not add an authenticator challenge to those flows.

Security changes require a session created within the last five minutes. The **Sign in again** link supports password, passkey and configured provider sign-in and returns to Security. Password changes and authenticator changes also require the current password. A reset link expires after one hour and revokes existing sessions when used.

Security mutations and method removal serialize per parent inside database transactions, with live session ownership, expiry and freshness checked after acquiring the lock. Password rotations and authenticator/passkey writes use the library handlers within that transaction. Explicit OAuth linking binds the callback to its initiating session and rechecks that authority at the final account insertion, including when the callback consumed its state before revocation. The temporary session reference is cleared before storage. Passkey and provider sign-in also recheck the exact verified method during session insertion under the same parent lock, so a removed method cannot finish an in-flight sign-in. These temporary authority fields are never accepted from clients or retained in account/session records. Removing a provider identity records it in `amp_auth_removed_identities` in the same transaction; the account trigger refuses an implicit link to a removed identity, or to a parent with an authenticator, under the same parent lock, and an explicit link clears the record.

Method removal is server-authorized. At least one usable password, configured provider or passkey must survive. A password counts only when password sign-in is enabled and the email meets this deployment’s verification requirement. AMP blocks Better Auth's separate raw removal endpoints, which cannot enforce this cross-method invariant. Other accounts' methods cannot be renamed or removed.

`tests/passkey-signup.integration.ts` drives real attestations and assertions from a software authenticator: atomic creation, abandoned and failed ceremonies, replay, cross-site requests, existing and concurrently taken emails, confirmation and passkey sign-in, and recovery by reset. `scripts/verify-passkey-sign-up-ui.ts` runs the browser flow with Chromium's virtual authenticator.

`tests/account-security.integration.ts` covers account ownership, origins, stale sessions, password revocation, authenticator verification and recovery, signed OAuth callback fixtures, simultaneous provider/passkey removal, competing password rotations, OAuth callbacks paused during token exchange, provider sign-in paused before session creation, and request-local provider identity isolation. `scripts/verify-accounts-ui.ts` exercises the real server with a virtual WebAuthn authenticator and checks revocation during passkey enrollment and sign-in, device-clock skew, and the interface at 320, 390 and 1280 pixels. Its screenshots mask setup secrets and recovery codes.
