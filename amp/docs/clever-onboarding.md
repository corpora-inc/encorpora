# Clever and direct school onboarding

AMP supports teacher-led pilots and institution-managed rosters using the same learners, classes and learning records. Classroom setup requires data authority but does not require a purchase, payment card or AMP operator approval. Commercial pricing is negotiated separately.

## Entry paths

| Starting point                           | Path to a learning class                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Teacher with no roster integration       | Sign in, open `/school/start`, confirm classroom authority, paste names or import CSV/Excel, review the roster, activate the pilot and open Start class.                                                                                                                                                                                                                                                                                   |
| School or district using Clever Complete | A Clever district administrator authorizes sharing, signs into AMP, confirms the institutional agreement and imports the roster. Connecting starts the district's pilot for every class it shares. Students practice the moment they sign in; teachers do nothing first.                                                                                                                                                                   |
| Institution without Clever               | Start classes directly. A school administrator asks for Clever AnySchool on the school's Integrations page, giving the setup email and accepting the agreement. An operator sends Clever's invitation, connects the district once the school has shared its data, and starts the import after the school's existing classes move in. AMP then uses the same roster API and model as Complete. See [Clever AnySchool](clever-anyschool.md). |
| Existing AMP school joining a district   | The school owner authorizes adoption into one specific district. Its administrator reviews the grant and any staff identity conflicts. Learners, evidence, classes and pilot dates keep their IDs.                                                                                                                                                                                                                                         |
| Existing AMP school moving to Clever     | Stage the first import, adopt the school if needed, and review exact school, person and section source-ID matches before starting synchronization. Names and email addresses never establish identity.                                                                                                                                                                                                                                     |

Clever's [AnySchool setup guide](https://dev.clever.com/docs/anyschool-rostering) requires provider enablement and a dashboard invitation that the institution completes. The request in AMP does not claim to have sent that invitation or connected an SIS. Teachers can start directly while the institution completes this step. An AnySchool district may have no Clever district administrator, so the agreement comes with the request and an operator connects the district. [Clever AnySchool](clever-anyschool.md) has the operator steps, what the school does, how AMP reads AnySchool data and the acceptance tests.

## Pilot and purchase lifecycle

A pilot is free for 30 days, then 14 days of full-access grace, then the paywall. There are two kinds, with the same dates, grace, extensions and expiry.

- **A connected district's pilot** (founder ruling 2026-11-20). Connecting a Clever district starts one pilot owned by the district. Both Complete and AnySchool connections do this, through `registerCleverConnectionIn`. It covers every class in the district: shared sections, sections shared in later syncs, and classes teachers make there themselves. No teacher starts anything, and no approval, license or seat check comes before a student's first practice. Its eligibility digest is the Clever environment and district ID, so reconnecting, or deleting and reconnecting the district, finds the same dates. A district connected before this rule gets its pilot, dated then, on its next roster sync or its people's next Clever sign-in. A class in the district never starts a teacher's own pilot, during the district's pilot or after it ends; a teacher pilot the class already had still counts. The overview's Seats card and the License page show "Free pilot · N days left", then "Grace period · N days left". While the pilot runs, no student is listed as needing a seat; a student in no class needs a class instead. Seats are negotiated separately, and a license can overlap the pilot.
- **A teacher's pilot**, everywhere else. A teacher's first class starts it. Later classes share its deadline; an already activated class cannot switch to a co-teacher's fresh pilot. Provider aliases and a verified mailbox are recorded as eligibility digests, so reconnecting or recreating an account cannot renew the trial.

Deletion removes account identity and classroom data according to its ownership while retaining only the minimal eligibility references and dates.

Expiry pauses new online practice and new workbooks. Reports, exports, issued materials and entry of their paper results remain accessible. Another valid pilot, license or grant continues access. An operator extends either kind of pilot with `npm run school:admin -- extend-pilot` (`amp_org_pilots` gives a district's pilot ID). A paid class scope requires current membership; leaving every purchased class invalidates and releases that seat. Overlapping school licenses count a learner once. Every extension has an auditable reason and reference.

The teacher's buyer link contains aggregate adoption information, expires after 30 days and grants no account or school authority. Negotiation, quotes, POs and invoices can precede activation. The operator commands `purchase-status` and `activate-purchase` record that process. Activation uses existing records and is idempotent by purchase request. `issue-license` supports selected classes or an entire school/district subtree.

## Identity and source ownership

Clever identities are keyed by environment, district and user ID. Sandbox and production cannot collide. Staff can sign in without a mailbox; a Clever email is not proof of mailbox ownership. Linking to an existing AMP account requires a fresh authenticated linking flow. Student sessions retain AMP's isolated `st_` capability and cannot become parent sessions on a shared device. See [Clever sign-in](clever-auth.md).

The roster adapter imports districts, schools, multi-role users, multi-school memberships, sections with co-teachers, courses and terms. Optional fields may be absent. Contacts are recognized but do not create guardian permissions. AMP retains an allowlisted source snapshot and discards sensitive fields it does not use. AMP's birth year is a school-year cohort ("born 2016" is in grade 4 in 2026-27). The school's grade sets it exactly; PreKindergarten and Transitional Kindergarten count as one year before Kindergarten and Preschool as two. When a student has no placeable grade (Ungraded, Other or none), the cohort year of their Clever date of birth fills in. Only that year is kept, never the full date. A learner's birth year never changes after their first answer. One person has one learner within a district, even across several schools or sections. A section's term gives its class dates unless that term had already ended before AMP first held the class. Clever's sharing decides whether a section is current, and term dates are optional and not guaranteed, so a section shared under such a stale term (or none) uses the connection's calendar for this school year and keeps taking practice. A term that ends after its class began ends the class, as any AMP session does. Sections that share a name at one school get the section's SIS ID in parentheses, or its Clever ID when SIS IDs are missing, repeated or long, so a teacher can tell them apart; a teacher's own rename is kept.

Clever v3 `staff` are school administrators (principals, counselors, tech leads). Staff administer each school they are listed at, the same school authority an AMP school admin holds. `PortalOnly` is Clever's default staff role ("the standard portal experience") and `SchoolTechLead` adds Clever-side powers; both administer their schools in AMP (migration `0148`). A source-owned school admin role stays valid only while the roster still lists that person as staff of that school and their signed-in Clever identity still carries `staff` (migration `0142`). Clever never takes over a hand-granted admin role, so a school's founder keeps it if Clever later demotes or unshares them. Connecting or reconnecting a district still requires a Clever district administrator. A teacher's access follows their class enrollments. Multiple supported roles combine their scopes, while student and contact identities cannot also hold staff roles. See Clever's [staff-role definitions](https://dev.clever.com/docs/api-v3-upgrade-guide).

Full snapshots and Events update source-owned memberships. Manual memberships remain independently controlled. Unshared records are archived and can be restored under the same provider IDs. Learning evidence is not deleted by a roster removal. Privacy deletion tombstones identities so synchronization cannot silently recreate the learner. Events, source records and the resulting roster commit atomically. Invalid, partial or forbidden responses cannot trigger a removal sweep.

A separate worker requests a full snapshot daily and processes Events every five minutes, so a student added in the SIS reaches AMP within minutes. API handlers only queue work.

Events are on for every connection by default, whether the district connected itself, an operator connected it or AnySchool did (migration `0149` turned them on for connections stored with the old `false` default). An operator turns them off with `npx tsx scripts/clever-sync.ts bind <district-id> <tenant-id> no-events`, and back on with `... events`. A reconnect without the flag keeps the connection's setting, so an opt-out survives the district re-running connect.

Each full snapshot reads the newest event id before it reads the roster, and stores it as the Events cursor once the snapshot commits. Changes made while the snapshot is read come after that cursor, so the next Events run replays them; replay is idempotent because each event carries the complete object. A district whose feed is empty at that moment still gets a baseline (`events_baseline_at`); its next Events run reads the feed from the start. Without a baseline the connection takes a full snapshot.

If Clever refuses `/events` (401 or 403 during an Events run, or any 4xx when a full snapshot reads the newest event id), the run takes the full snapshot instead and succeeds. Rate limits and server errors are retried and still fail the run. The connection records `events_unavailable_at`, the worker logs `[schools] Clever Events refused` with the connection id and status, `sync` reports `"events":"unavailable"`, and the district moves to the daily schedule. Each daily snapshot asks again; the first one Clever answers clears the mark and returns the district to five-minute Events. On-demand requests require a school or district administrator and are limited to one per connection per 15 minutes. Repeating connection setup does not bypass this limit. Deployment-wide claims prevent duplicate work; interrupted runs are recovered. Repeated failures back off exponentially from one minute to 512 minutes and reset after success. Deleted people are skipped and entered in the connection review queue; their deletion does not stop other roster changes.

Connection status reports queued, running, retrying, delayed or ready synchronization, with request, attempt and retry timestamps. A request or due retry waiting more than five minutes, or a running attempt older than the worker's 30-minute deadline, reports delayed. This detects missing or interrupted job processing without granting or denying school access. The connection and imported records are preserved; an administrator can retry within the request limit. Operators should check the worker schedule, credentials and job logs when processing is delayed. Bootstrap administrator proofs do not count as worker attempts.

Each worker pass visits unattempted districts first, then districts with the oldest attempt. An interrupted import therefore yields to other districts on the next pass. Database claims prevent concurrent imports of the same connection.

For a staged connection, the worker caches the source for adoption review without provisioning people, classes or memberships. An administrator starts the import after reviewing the matches. Adoption authority is rechecked with a single provider-user read. The school selector reads stored school records; a selected-school preview reads at most 5,000 source records and refuses larger previews. A provider revocation ends source access; reauthorization uses a short-lived onboarding proof and a current provider-role check before normal access can resume.

## Worker deployment

Run `node --import tsx scripts/clever-sync.ts sync all auto` in a separate job every minute. The command checks each connection's due time and retry deadline, processes districts sequentially, and clears only requests it consumed. It first asks the database, in one query, whether any connection is due a sync (or, with LMS Connect configured, whether any is active). If none is, it exits without loading the sync code: about 0.2 s and 90 MB instead of 3 s and 400 MB on a laptop (the old idle run took 20 s in the cluster pod). A just-connected district or a "Sync now" request is due at once, so it still starts within a minute. Use [the CronJob template](../deploy/clever-sync-cronjob.yaml) with the release's API image and a worker Secret containing `AMP_DATABASE_URL`, `AMP_CLEVER_ENVIRONMENT`, `AMP_CLEVER_CLIENT_ID`, `AMP_CLEVER_CLIENT_SECRET` and `AMP_CLEVER_API_VERSION`. Set the same API version for the server and worker: `3.0` for a Rostering v3.0-enabled app, or `3.1` when that version is enabled for the app. Rostering v3.0 provides the data required for this onboarding. Enhanced demographics and LMS Connect are separate capabilities; LMS Connect needs 3.1 and `AMP_CLEVER_LMS_CONNECT=enabled`, and runs in this same job ([Clever LMS Connect](clever-lms-connect.md)). Substitute both template placeholders before deployment. The template requests one CPU and 1 GiB memory, limits memory to 2 GiB, and prevents overlapping jobs. The requests stay sized for a bulk import (1.29 GiB measured), which is CPU-bound under a 30-minute deadline; an idle pod now holds them for about a second. Verify capacity for the largest district; [measurements and lock-capacity requirements](clever-performance.md) include synthetic fixtures and their limitations.

Do not run this command inside an API container. API maintenance independently reconciles seats, updates connection reviews and expires provider sessions and OAuth flows. Sign-in attempts the roster attachment lock without waiting; a busy apply defers attachment until a subsequent authenticated request. An identity conflict expires the session. Completed synchronization runs older than 30 days are removed once no source binding or membership references them.

## Sandbox and launch

1. Create a development application and obtain Rostering API v3.0 or v3.1 and AnySchool access from Clever. Configure `AMP_CLEVER_API_VERSION` for the enabled version in both the server and worker. Default developer credentials may have only basic SSO scopes.
2. Configure the exact redirect URI `<AMP origin>/api/v1/school/sso/clever/callback`. Enable supported user types and Events in the provider dashboard. Store credentials in secret storage, never in the repository or a shared transcript.
3. Apply migrations and configure the variables in [Clever sign-in](clever-auth.md). Set `AMP_CLEVER_TEST_DISTRICT_ID` privately and run `npx tsx scripts/clever-probe.ts` with `AMP_CLEVER_ENVIRONMENT=sandbox`. Its output contains capability status and record counts only. A 401/403 is a capability failure, not an empty roster.
4. Complete a real development-app round trip: district sharing, initial roster, teacher/student sign-in, sharing removal and restoration, school/class transfer, co-teacher, multiple roles, zero-section user, missing optional fields, terms/courses, Events and full resync. Exercise AnySchool invitation, source upload and import separately, following the manual acceptance list in [Clever AnySchool](clever-anyschool.md).
5. Use Clever's [Secure Sync certification guide](https://dev.clever.com/docs/secure-sync-certification-guide) and certification dataset. Request the certification form through the partner contact. Fixture tests and a successful token request do not establish provider certification or production readiness.

`npx tsx scripts/clever-sync.ts sync <connection-id> full` performs an explicit full repair; `sync all auto` runs configured connections. Credentials and tokens are not written into sync logs. `npm run school:admin -- school-queue <private-input.json>` lists connection requests, commercial follow-up and connection-release reviews. Its `clever` section counts launched and staged schools per environment, because Clever's partner license counts schools. It lists each connection, and with Clever credentials also the districts that shared data but are not connected. AnySchool invitations are sent from Clever's dashboard. `anyschool-invite`, `anyschool-connect` and `anyschool-import` record and carry them through. `connection-request-status` closes a request. Review disconnected or expired institutions before freeing an upstream slot. Capacity is not an onboarding gate.

Use `AMP_TEST_DATABASE_URL=<dedicated test database> npx tsx scripts/verify-clever-scale.ts --run` for the synthetic district benchmark. It checks stable IDs, repeated imports, scoped access, transfers and empty Events polling, and reports query counts, time and memory. It uses a disposable schema and synthetic HTTP responses. See [roster performance and privacy](clever-performance.md) for measured district workloads, memory use and PostgreSQL lock sizing for mass changes. These measurements do not include provider latency or establish production capacity.

## Production go-live

Clever certifies AMP, then clones the development app into a production app. The production app has its own client ID and secret. Its identities live in Clever's production namespace, so nothing from the sandbox carries over.

1. Configure the production app in Clever's dashboard to match the development app:
   - redirect URIs: `https://amp.corpora.inc/api/v1/school/sso/clever/callback` first, since Clever Portal and Instant Login use the first URI;
   - supported user types: district administrators, school administrators and staff, teachers and students; not contacts;
   - Events on;
   - data access the same as the development app, with contacts off;
   - the same API version (`3.0`, or `3.1` once Clever enables it; LMS Connect needs `3.1`);
   - the district setup wizard copied from the development app.
2. Add the production credentials to the prod environment's secret, `corpora-amp-prod-env`: `AMP_CLEVER_CLIENT_ID`, `AMP_CLEVER_CLIENT_SECRET`, `AMP_CLEVER_ENVIRONMENT=production` and `AMP_CLEVER_API_VERSION`. Add `AMP_CLEVER_DISTRICT_SIGNUP_URL` too if the production app has a schools.clever.com signup link. Never put the values in the repository or a transcript.
3. Set the deploy variable `DEPLOY_CLEVER_SYNC_ENABLED=true` on the `corpora-amp-prod` deployment environment. It unsuspends the roster worker; unset or `false` keeps it suspended.
4. Deploy prod. Before anything changes, the deploy runs two checks. Its preflight refuses to start the worker without a complete production set. `npm run infra -- env check --env prod` requires all four Clever settings or none, and `AMP_CLEVER_ENVIRONMENT=production`. It then runs the API's own Clever loader, so a padded value or a bad signup URL fails here, not at startup. A refused deploy changes nothing.
5. Verify:
   - `https://amp.corpora.inc/api/v1/auth-config` shows `"clever":true`;
   - a district administrator connects a district at `/school/connect`;
   - the worker's first run completes and imports that district's roster.

Roll back by setting `DEPLOY_CLEVER_SYNC_ENABLED=false`, removing the `AMP_CLEVER_*` lines from `corpora-amp-prod-env` and deploying prod. The variable alone stops the worker and keeps sign-in. Removing the settings turns off Clever sign-in. A suspended worker starts no new runs; a run already in progress finishes.

Once production is settled, a pull request can add `clever` to prod's declared groups in `infra/secrets.ts`. A secret rotation that drops the settings then fails the check instead of quietly turning Clever off. Rolling back after that also needs that line reverted.

## Limits

Provider access, institution sharing and certification are external prerequisites. A connected district exposes only what it shares. Existing Clever bindings cannot be silently repointed to another learner or institution; established duplicate identities need a reviewed resolution. District adoption grants are single-use, expire after seven days and recheck both parties' authority at acceptance. Learner names and school names are never matching keys.

Assignments and grade passback to Google Classroom, Canvas and Schoology are in [Clever LMS Connect](clever-lms-connect.md). That feature is off until Clever enables LMS Connect for the app, and it is not yet tested against a live district. Teacher referral commissions and public seat-pack checkout are outside this onboarding implementation. AMP's core remains adaptive practice.

### Retrying a busy connection

When a roster apply holds the connection lock, connecting returns HTTP 409 with
`{error: "clever_sync_already_running", retryAfter: 1}` and `Retry-After: 1`.
Retry after that delay. A deferred administrator attachment does not create a
person or grant bootstrap authority. Staff sign-in defers attachment during lock
contention and can attach on a later session read.
