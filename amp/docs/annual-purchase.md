# Parent annual web purchase

AnnualPurchase is the parent-facing annual subscription workspace. It receives a stable parent identity, an access token, a Back callback, and an optional access-change callback. Mount it from Family Access, never from a child's practice question. A token refresh for the same identity preserves the screen; changing identity discards its requests and selection. The host may pass a `processing`, `canceled`, or `account` return hint from the billing redirect. Those hints are explanatory only and never prove payment.

The purchase workspace keeps the learner selector, annual amount, renewal essentials, status, and primary action visible on ordinary phone screens. Cancellation and refund details open in a focused Terms panel with keyboard focus restored on close. Payment-processing returns show verification status and Check access, without another purchase prompt.

The authenticated `GET /api/v1/billing/offer` endpoint returns an explicit unavailable state when Stripe is not configured. A configured offer is checked against the merchant's active annual price and cancellation portal before display. The web workspace accepts USD offers only, displays the configured amount rather than a default price, identifies sandbox mode, and explains yearly renewal, one-learner scope, final tax review, and cancellation. Unsupported currencies fail closed in offer presentation. No merchant credentials or provider resource identifiers appear in the offer.

A parent selects an owned learner and the workspace checks `GET /api/v1/billing/status/:learnerId`. Current and future ledger grants prevent another purchase. Open checkout can be resumed; expired checkout is closed and retried once with a fresh request identifier. Network failures preserve the request identifier. The server also serializes reservations for each learner and rechecks consent and existing access before returning a payment link. A concurrently acquired license can stop checkout even if the screen previously offered purchase.

Checkout returning successfully is not fulfillment. Completed checkout without a verified ledger grant displays payment processing and offers Check access. The signed-webhook worker verifies the annual invoice and creates the grant. A later full refund revokes the grant. A previously bound subscription without current access requires billing review before a replacement subscription can be started; the workspace does not infer cancellation or permit an overlapping replacement. Billing management remains available after consent withdrawal and when an offer cannot be loaded.

The workspace directs card entry only to Stripe's hosted checkout and cancellation only to its hosted billing portal. It never collects card details. Cancellation stops future renewal according to the verified portal's end-of-period setting; it is not a refund request. Learning-data deletion does not cancel a subscription. Refunds and unresolved subscription bindings require the merchant's support and reconciliation process.

## Validation and release boundaries

Run `npm run test:annual-ui`, `npm test`, `npm run tsc`, and `npm run build`. With `AMP_TEST_DATABASE_URL` pointing at a disposable PostgreSQL database, `npm run test:db` verifies ownership, concurrent idempotency, expired-session recovery, delayed verified grants, existing-access protection, and consent changes during a held provider lookup. The annual browser fixture covers exact sandbox copy, compact screen bounds, stable retry identity, account-switch/unmount response suppression under React StrictMode, and unavailable billing. Browser fixtures use synthetic offers and intercept every payment navigation; they do not charge a card.

Before a hosted paid release, configure and verify the actual merchant offer, parent enrollment and consent process, support/refund policy, tax treatment, webhook worker, billing return routing, and ledger operations. Exercise payment, renewal, failed renewal, cancellation and refund in the merchant sandbox. These checks require operator-owned provider configuration and are not replaced by repository fixtures. Native app-store purchasing and native external-payment policy handling are outside this web flow. See [Stripe integration](stripe.md) and [deployment requirements](deployment.md).

Stripe requires webhook-based subscription fulfillment because a customer may never reach the return page. Amounts use provider minor units; this workspace deliberately supports USD rather than guessing global currency precision. See [fulfillment](https://docs.stripe.com/checkout/fulfillment) and [currency amounts](https://docs.stripe.com/currencies).
