# Tabletop: leaked database URL · 2026-11-27

Exercise of [incident-response.md](../incident-response.md) against production, 17:25–17:50 UTC, run by an agent on the incident lead's machine and credentials. Nothing was rotated, disabled, scaled, suspended or revoked. Every command ran read-only or as a server-side dry run. Afterwards `amp-api` and `amp-sql-proxy` were still at 2 replicas, every CronJob kept its suspend state, the deploy workflow was `active`, and the env secret was still at the same version.

Redactions: the cloud project is `$PROJECT`, identities are shown by kind, and AMP's data counts are in the private exercise record (`operations/AMP_INCIDENT_ACCESS.md` in `corpora-inc/infra-private`). No learner, parent or teacher data was printed: queries returned counts only.

## Scenario

At 17:25 a reader notices AMP's production `AMP_DATABASE_URL`, with the `amp_prod` password, pasted into a comment on a public pull request. It has been public for an unknown time.

Triage: **level 1**. The credential reads all student and family data. The school clock has not started, because nothing shows the credential was used.

Outcome: with no `connect` from an unexpected identity, the tabletop concludes **no confirmed access**. The real response would still rotate the password, end the older sessions, record the determination and send no notices. Had an unexpected identity connected, everything `amp_prod` can read would count as exposed: notify every school and teacher with a live agreement within 72 hours, and work through the state table for each family.
