# Tabletop: leaked database URL · 2026-11-27

Exercise of [incident-response.md](../incident-response.md) against production, 17:25–18:05 UTC, run by an agent on the incident lead's machine and credentials. The exercise rotated, disabled, scaled, suspended and revoked nothing. Each command ran read-only, as a server-side dry run, or as its `count(*)` form; the few that cannot be dry-run had their flags checked in `--help`. Afterwards `amp-api` and `amp-sql-proxy` were still at 2 replicas, every CronJob kept its suspend state, the deploy workflow was `active`, and the env secret was still at the same version.

Redactions: the cloud project is `$PROJECT`, identities are shown by kind, and AMP's data counts and the access-control and logging details behind gap 3 are in the private exercise record (`operations/AMP_INCIDENT_ACCESS.md` in `corpora-inc/infra-private`). No learner, parent or teacher data was printed: queries returned counts only.

## Scenario

At 17:25 a reader notices AMP's production `AMP_DATABASE_URL`, with the `amp_prod` password, pasted into a comment on a public pull request. It has been public for an unknown time.

Triage: **level 1**. The credential reads all student and family data. The school clock has not started, because nothing shows the credential was used.

Outcome: with no `connect` from an unexpected identity, the tabletop concludes **no confirmed access**. The real response would still rotate the password, end the older database sessions, delete every adult session and reset token (the URL was public, so a copy cannot be ruled out), record the determination, and send no notices. Had an unexpected identity connected, everything `amp_prod` can read would count as exposed. Then: notify every school and teacher with an agreement within 72 hours, tell Clever if rostered data was involved, and work through the state table for each family. Because live session tokens were in reach, the Arizona row would be decided on the facts, not waved off.

| Gap | Where it is handled |
| --- | --- |
| 1. No operator command revokes sessions in bulk. Session and provider tokens are stored as issued, and bearer tokens need no signature. Rotating `AMP_ACCOUNTS_SECRET` would orphan authenticator secrets (no parent had one today). | [#2555](https://github.com/corpora-inc/encorpora/issues/2555) |
| 2. No uptime check or alert policy covers AMP production. Detection relies on deploy smoke checks and reports. | free2z/tuzi#3025 (private) |
| 3. Permission to connect to AMP's database is broader than AMP needs, and the database cannot attribute reads. | free2z/tuzi#3026 (private) |
| 4. A credential pasted into an issue or comment here is not scanned for. | corpora-inc/infra-private#179 (private) |
| 5. The deploy poll would undo a manual take-down. A password change leaves open sessions alive. | Fixed in the procedure: disable the poll first; terminate older sessions. |
| 6. The point-in-time clone was not exercised. It copies all production data; run it in the timed restore drill. | free2z/tuzi#2798 (private, recovery exercises) |
| 7. Request logs carry no user id, so a taken-over account's actions are traced by address and `amp_school_events`. | Documented in section 5. Not filed: account sessions record their addresses. |
