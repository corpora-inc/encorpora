# AMP

AMP is an independent TypeScript/PostgreSQL mathematics product. Follow the repository trunk procedure. AHA's app-specific identity and persistence constraints do not apply here.

- Before adding or changing a problem type, follow [the problem-type definition of done](docs/problem-type-checklist.md). Its registry-derived source-artifact check runs on every AMP pull request and merge-queue candidate; worksheet builders and print inputs must work before merge.

- Before changing who signs in, who sees what, places, roles or licenses, read [the product model](docs/product-model.md): people, places, sign-in, prices and every screen by person, with what is decided and what is not built yet.
- Marketing describes AMP as a complete math curriculum from counting to precalculus (#1996). Coverage audits are internal engineering tools for finding and closing gaps in the product, not limits on marketing copy. Never add self-undermining caveats; keep only qualifiers that a funding program or the law requires. In engineering, a mapped skill is not an implemented or verified skill.
- Every new skill must join a stable exposure objective in `src/curriculum/selection.ts`. Fine-grained graph steps and new generators share that objective’s budget; creating an objective is an intentional curriculum-mix change. Keep frequency weights separate from difficulty.
- Follow [the pathway selection model](docs/pathway-selection.md) for adaptive metadata. Preserve direct evidence separately from inferred prerequisite support; do not award ancestor mastery from a downstream answer.
- Put selection tuning in the validated, versioned `src/learning/practice-policy.ts` configuration. Inject a compiled policy per run; test default equivalence and changed-parameter behavior. Keep learner-estimator and evidence-projection revisions separate.
- Mathematical truth is server-owned and deterministic. Never send grading secrets in a public problem payload.
- Preserve immutable problem versions and evidence. Retries must not duplicate attempts or progress credit.
- Parent/learner authorization must be enforced on the server. Development authentication is loopback-only and forbidden in production.
- Content authors and independent reviewers are separate workers. Do not certify a generator by calling its own answer function twice.
- Public copy explains the current product without conversation history. Provider approval requires evidence from the specific program.
- **Local gates (fast-building stage, fail forward):** before pushing, run `npm run tsc`, `npm run test:core`, and only the database or browser scripts for what you changed. `npm test` runs the core, content and inventory suites when a full local check is needed. The exhaustive inventory is a post-merge content check; it is not a pre-merge gate. Don't run the whole `test:family-ui` chain locally; CI runs it.
- **Routine CI:** `.github/scripts/amp_ci_plan.py` selects parallel `amp-core`, `amp-database` and `amp-build` jobs behind the existing `amp` and required `ci-gate` aggregates. PRs and the merge queue run compilation/build checks, contract smoke tests, changed test entrypoints and focused database checks for protected account, money, consent and privacy paths. Broad affected regression suites run asynchronously on main; fix failures forward. Shared helpers, fixtures, migrations, dependencies and unknown inputs select broad main validation. Test-only edits select their entrypoints; math-oracle edits (`scripts/*_oracle.py`, `scripts/independent-math-review.py`) select the tests that name them; app-screen changes skip database work. Changes to the selection policy or its workflows run full validation on the PR too. Add planner regression cases when changing these boundaries; do not add required branch-protection contexts.
- **Deep checks:** `amp-browser` and `amp-content` run in the independent `AMP deep checks` workflow, selected by changed paths on main and also nightly or manually. Content checks include the full inventory and reuse only a successful result matching the exact content inputs and runner environment. Scheduled and manual runs force revalidation. The fingerprint policy is `.github/scripts/amp_inventory_paths.py`; unknown AMP inputs are included. Failures file or update a follow-up issue. Fix those failures forward with a small PR; they do not hold routine deployment.
- **Launch acceptance:** before a launch, including a paid acquisition campaign, require successful `amp`, `ci-gate`, `amp-browser` and `amp-content` checks on the launch candidate commit. Dispatch full `CI` and `AMP deep checks` runs; narrow selections do not establish full launch acceptance. Manual deep checks bypass content-result reuse. Routine deployment eligibility alone does not establish launch readiness.
- **Green ships.** Routine production deployment selects the newest `main` commit touching `amp/` with successful `amp` and `ci-gate` checks in the same `CI` run at their latest attempt. Failed, cancelled, skipped or missing checks do not qualify. If the newest commit is not green, the poll can select an earlier green commit but never replace a live release with an older one. `scripts/release-status.sh` shows what is live and why ([Releases](docs/deployment.md#releases)).
- Money, consent and privacy paths (`src/billing`, `src/parent-consent`, `src/privacy`, `src/family`) always get database tests in the PR itself.

## Interface acceptance

- Family navigation has three destinations: Today, Progress and Settings. With one child, Progress opens that child’s record directly. Several children share a comparison with explicit links to each record. Workbooks, time and reports belong to Progress; people and sharing belong to Settings.
- Family is a parent's stable home. A child's Practice action starts that child directly; show a clear Back to family in practice. Adult practice is an optional You entry within the family, never a competing primary journey or a remembered home that displaces the family. Keep simulations out of children's primary actions. The selected learner must remain explicit in session state and every answer must reach that learner's record.
- Curriculum browsing should lead directly into practice for the child whose curriculum is being viewed. Offer practice from areas, skills, and problem types; preserve the chosen filter across consecutive problems and reloads, with a clear return to mixed practice. Show videos at the specific skill or problem type. Broad areas lead into their skills, not an expanding dump of every video. Use one meaningful lesson title and compact navigation controls. Label inferred levels as estimates. Default activity summaries to daily and keep sparse histories compact. Daily and weekly time share chart styling and hover, tap and keyboard details. Begin at the first interval with practice; preserve quiet intervals after it.
- **Purchasing must work (Skylar, November 15, 2026).** Parents choose a plan and pay, or choose a funding program and plan, enter the invoice name, and download the invoice. Do not disable plan selection or invoice fields because learning consent is incomplete. Do not show internal consent states as dead ends. Use the existing purchase-based enrollment flow when payment establishes permission; keep any legally required notice within the working purchase flow, with an immediate action. Invoice preparation and learning authorization are separate operations. Every added restriction must cite an actual applicable requirement; speculative compliance is not a product requirement. Verify payment/invoice completion with a returning parent whose learner already exists, including incomplete consent, rather than testing only a fully approved fixture. Keep purchase agreement in the primary action; do not add a separate checkbox, modal or consent screen. Make detailed terms and policies readable and downloadable from Privacy. Education-fund invoice creation should start eligible learners immediately, with a clear submission deadline and visible payment status.
- Each screen and tab has a URL; browser history, refresh and direct links restore it. Verify Family → a child’s Practice → browser Back without opening curriculum first: Back restores the parent’s originating page, Forward resumes that same child, and reload preserves the answering identity. A shared-device handoff is local to the tab; it must not broadcast a second account-session change.
- Family and learner data share one account-scoped store. Refresh it on navigation and mutation, and reject responses from an obsolete account session.
- Present an action only when its prerequisites are satisfied. Guide new parents through consent, access and learner setup without bypassing server authorization.
- Errors explain the failed action and recovery, are logged without private request data, and appear inline in reserved space or as fixed overlays. Async loading and feedback must not move existing controls.
- Use shared, accessible controls with visible focus, readable labels and touch targets of at least 44 px. Checkbox inputs and their indicator, keyboard, focus and disabled behavior belong to `src/web/ui/Checkbox.tsx`. Compose `CheckboxControl` within feature labels; use `Checkbox` for full confirmation rows. Do not create raw checkbox inputs or custom checkbox roles in feature components. `npm run lint:controls` enforces that ownership during the build.
- Audit interactions alongside geometry: typing, long paste, deletion to empty, clear/reset, Escape, focus, browser Back/Forward and reload. User-entered filters must stay within route limits, and malformed shared search values must recover without replacing the screen with an error.
- Review complete composed screens in guest, signed-in and paid states. Inspect visual hierarchy, typography, alignment and control weight in screenshots; overflow and touch-target assertions alone do not establish visual quality. Keep skill titles readable rather than truncating them to make room for secondary controls.
- Verify real browser behavior and attach synthetic screenshots at 320, 390, 768 and 1280 px in light and dark themes. Measure overflow and bounding boxes during loading, validation and failed requests; verify learner state across navigation.

### Frontend architecture (non-negotiable, enforced in CI)

AMP's web app is built to an elite engineering standard, not as a pile of one-off screens. An audit on 2026-11-16 found 88 redirects, 39 query-string handoffs, 14 separate "where next" functions, the current learner held in 7 places, and about 13 pay surfaces. Those produced redirect chains and a Back button that hung the tab. Never reintroduce these patterns. Ratchet tests and lint hold every count to "only falls" (`tests/architecture-ratchet.test.ts`; lower its baseline as counts fall).

- **Canonical global state.** Every fact has exactly one owner:
  - Server data lives in the TanStack Query cache, behind a key factory, and changes only through mutations that invalidate everything that shows it.
  - Client state (current learner, current place, flow drafts, preferences) lives in typed zustand stores keyed by account.
  - Components read through hooks and selectors. Never drill props, never copy state into `useState` and sync it with effects, and never build a context as an ad-hoc store.
- **URLs name screens, not state.** A path names the screen and its subject (`/family/<id>/today`, `/pay/<learnerId>/…`).
  - No query strings carry app state between screens (`?learner=`, `?from=`, `?return=`, `?interval=`). The one exception is a third party's return value, such as Stripe's `session_id`, read once and resolved.
  - Back, Forward, refresh and shared links work by construction.
- **No redirect chains.**
  - Compute a navigation target once, from canonical state, before navigating, then link straight to it.
  - Redirects exist only for a legacy URL or the sign-in gate: one hop, never chained, never based on how the page was reached.
  - No effect navigates, and nothing navigates during render.
  - `/` never redirects.
- **One component per job.** Screens render through `ui/Page` and `PageHeader` (one width scale, one header). Lists use `ui/ColumnList`. Use the shared controls in `ui/`. Never add a page-specific width, header or back link, a second dialog system, or a raw native control.
- **No in-page Back control. Tabs, menus and the browser navigate; flows use the shared stepper; contextual screens are overlays that close to the screen behind them.** The stepper is `ui/FlowSteps`; `tests/page-layout.test.ts` fails on a new Back.
- **Compose capabilities, never reuse whole pages in a new context.** Build each capability (add children, choose a plan, give consent, a skill's detail) as a self-contained component with its own data hooks and no route knowledge. Compose it where it's needed: inside a first-run step, in a sheet over Settings, in an overlay over a child's page. Never send someone through another flow's page or URL "with a different context" (for example /start/parent to add a child from Settings).
- **Contain failure.** Route errors render inside the app shell with the menu intact. No silent `.catch(() => null)`. Every error is logged and shown inline or as a toast.
- **Hooks rules are law.** Follow ESLint's react-hooks rules (`rules-of-hooks`, `exhaustive-deps`, `set-state-in-effect`). Fix a violation by deriving state or moving work to an event handler or loader, never with a disable comment without a written reason.

### Web application boundaries

Follow [the web architecture](docs/architecture/web-app.md). New auth and onboarding screens live in `src/web/features/`; typed TanStack routes and providers live in `src/web/app/`. `main.tsx` only bootstraps providers and the router. TanStack Query owns the account-scoped `/me` resource, including its Family projection; zustand owns selection and memory-only form drafts. Server mutations invalidate that canonical resource. Shared accessible controls and theme tokens live in `src/web/ui/`. The legacy host bridges Family, billing, trial, lessons and practice until their feature migrations; do not add new screens to it.

- **One app frame.** Every signed-in app screen sits in `app/AppShell.tsx`: the logo in one spot, the group's tabs from `ui/Tabs.tsx`, one drawer. Give a new route its `staticData.space` and its place in `features/navigation/shell-frame.ts`; its tabs, actions, drawer and words come from the space ([spaces](docs/architecture/spaces.md), `features/spaces/`). Never draw a second header, logo or drawer, and never branch on an org's kind or a space inside a shared widget (`npm run lint:navigation`). `scripts/verify-app-shell-stability.ts` must stay green.
- **A wait on the server always moves, and looks the same everywhere** (`src/web/ui/loading.css`). A whole screen uses `LoadingScreen`; a wait inside a screen uses `Loading` from `ui/Loading.tsx`, never plain "Loading…" text; a pressed button sets `aria-busy` on that button only, which swaps its label for the moving wave; a reserved block adds the `amp-skeleton` class. `scripts/verify-loading-ui.ts` fails on a blank, still wait.
